title: "Errors"
description: "Every error has a type, a stable code and a message, and often a hint about what to do next."
---

Fissient uses standard HTTP status codes. `2xx` means success, `4xx` means the request was refused for a reason given in the body, and `5xx` means something went wrong on our side.

## The error object

```json
{
  "error": {
    "type": "policy_limit",
    "code": "max_order_exceeded",
    "message": "Order of $900.00 exceeds the user's max order size of $500.00.",
    "hint": "The user's policy caps order size; quote less, or raise max_order_usd with a full key.",
    "reasons": [
      {
        "code": "max_order_exceeded",
        "message": "Order of $900.00 exceeds the user's max order size of $500.00."
      }
    ],
    "request_id": "req_074914b9658848a482c9"
  }
}
```

<ResponseField name="type" type="string">
  The category of error. Use it for broad handling. See the table below.
</ResponseField>
<ResponseField name="code" type="string">
  The exact constraint that was hit. Stable, and safe to branch on.
</ResponseField>
<ResponseField name="message" type="string">
  A description for developers. The wording can change, so don't parse it.
</ResponseField>
<ResponseField name="hint" type="string">
  What to do next. Present on common errors.
</ResponseField>
<ResponseField name="reasons" type="object[]">
  For eligibility and policy refusals, every reason that applied, each with a `code` and `message`.
</ResponseField>
<ResponseField name="details" type="object">
  Structured data about the error, such as `issues` for validation failures or `candidates` for an ambiguous instrument.
</ResponseField>
<ResponseField name="request_id" type="string">
  The id of the request. Include it when you contact support.
</ResponseField>

## Error types

| Type | Status | Meaning |
| --- | --- | --- |
| `invalid_request` | `400` | The request is malformed or a parameter is invalid. |
| `authentication_error` | `401` | The API key is missing or invalid. |
| `permission_denied` | `403` | The key isn't allowed to do this. |
| `not_found` | `404` | The object doesn't exist, or isn't visible to this key. |
| `conflict` | `409` | The request conflicts with the current state. |
| `not_eligible` | `422` | The user isn't allowed to make this trade. |
| `policy_limit` | `422` | A guardrail on the user refused it. |
| `insufficient_funds` | `422` | The user doesn't have enough cash or units. |
| `quote_error` | `422` | The trade can't be priced or executed as requested. |
| `rate_limited` | `429` | Too many requests. |
| `internal_error` | `500` | Something went wrong on our side. |
| `service_unavailable` | `503` | A dependency is temporarily unavailable. Retry shortly. |

## Handling errors

Branch on `code` for cases you handle specifically, fall back to `type`, and treat anything unknown as a generic failure.

```javascript
const res = await fetch("https://invest-api.blink.cash/v1/quotes", { method: "POST", headers, body });

if (!res.ok) {
  const { error } = await res.json();

  switch (error.code) {
    case "quote_expired":
      return refreshQuote();
    case "max_order_exceeded":
      return show("That's above your order limit.");
    case "insufficient_funds":
      return show("You don't have enough cash for this. Add money and try again.");
  }

  if (error.type === "not_eligible") return show("This isn't available in your country.");
  if (res.status >= 500 || res.status === 429) return retryLater();

  console.error(error.request_id, error.code, error.message);
  return show("We couldn't complete this. Nothing was traded. Please try again.");
}
```

<Tip>
  Write the messages your users see yourself. `message` and `hint` are written for developers and agents.
</Tip>

## What to retry

| Situation | Retry? |
| --- | --- |
| `5xx`, `429`, timeouts, dropped connections | Yes, with backoff and the same [`Idempotency-Key`](/api-reference/idempotency). |
| `409 idempotency_in_progress` | Yes, after a short wait. |
| `409 quote_expired` | Create a new quote, then place a new order. |
| Other `4xx` | No. Fix the request first. |
